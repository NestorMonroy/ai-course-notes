\section{系统架构：单 Agent、虚拟机沙盒与 Coding 中枢}

\subsection{核心架构：Model + Sandbox + Tooling}

每个会话对应独立虚拟机，形成资源隔离与权限隔离。模型不直接“想象执行结果”，而是在可观测环境里调用命令、写代码、读取反馈，再进行下一步规划。这是把 LLM 从“回答器”升级成“执行体”的关键。

\begin{importantbox}{为什么虚拟机是结构性选择}
\begin{itemize}
    \item 安全：任务执行与用户主机隔离
    \item 连续性：长任务可在后台持续运行
    \item 可观测：完整日志可用于调试、评估和回放
\end{itemize}
\end{importantbox}

\subsection{单 Agent 优先而非 Multi-Agent 编排}

季逸超明确对当前“强行多 Agent 分工”的趋势保持保留。理由不是 Multi-Agent 永远错误，而是当前模型能力和工程成熟度下，多智能体协作的状态同步与错误传播成本高于收益。

\begin{warningbox}{Multi-Agent 早期最常见的失败模式}
\begin{enumerate}
    \item 任务切分过细，通信开销吞噬执行收益
    \item 状态不同步导致重复劳动或冲突操作
    \item 故障定位困难，责任边界不清晰
\end{enumerate}
\end{warningbox}

\subsection{Coding 作为统一动作空间}

访谈里“Coding 是灵魂”并非口号。Coding 的本质价值是统一动作空间：无论是数据处理、网页生成、自动测试还是工具编排，都能被降解为代码与命令执行。这样系统复杂度不会随工具数量线性膨胀。

\begin{knowledgebox}{统一动作空间的收益}
\begin{itemize}
    \item 降低策略学习难度：模型只需掌握一套高复用技能
    \item 降低产品维护成本：工具接口变化被代码层吸收
    \item 提高可解释性：失败可以通过日志和脚本回放复现
\end{itemize}
\end{knowledgebox}

\subsection{Tool 设计：以“删工具”替代“加工具”}

与很多 Agent 团队倾向于不断增加工具相反，Manus 更强调克制。因为工具越多，策略选择空间越大，误调用概率越高。高质量的通用工具通常比大量专用工具更稳。

\begin{importantbox}{工具治理的三条准则}
\begin{enumerate}
    \item 默认先尝试通用工具链（Code Execution, Shell, Browser）
    \item 只有在复用率足够高时才固化成专用工具
    \item 每次版本迭代都评估“可删除工具清单”
\end{enumerate}
\end{importantbox}

\subsection{本章小结}

Manus 的架构选择可以概括成一句话：用最少结构实现最多任务。单 Agent、沙盒执行、Coding 中枢与工具克制，共同服务于“稳定完成复杂任务”的目标函数。
