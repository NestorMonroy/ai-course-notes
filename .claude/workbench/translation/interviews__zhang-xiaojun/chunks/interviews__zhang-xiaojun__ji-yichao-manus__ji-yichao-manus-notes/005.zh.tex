\section{数据飞轮与评测：从 Benchmark 到真实体验闭环}

\subsection{Self-Evolving：不改参数也能持续变好}

访谈提出了一个重要点：改进不一定依赖模型再训练。通过累积失败模式、任务模板、策略提示和工具使用经验，系统可以在不改 base model 权重的情况下持续提升完成率。

\begin{knowledgebox}{Self-Evolving 的实践形态}
\begin{itemize}
    \item 失败案例归档：记录失败原因、修复路径、可复用补丁
    \item 任务模板升级：把成功轨迹抽象成可调用范式
    \item 运行时策略更新：在推理阶段动态加入约束和检查
\end{itemize}
\end{knowledgebox}

\subsection{用户反馈不是装饰，而是主训练信号}

季逸超强调“用户评分与 benchmark 分数常常不一致”。这意味着系统优化不能只盯代码正确率，还要包含展示质量、交互可读性、交付完整度等非结构化维度。尤其在 Agent 场景，用户判断的是“是否真的省事”。

\begin{warningbox}{评测偏差的典型来源}
\begin{itemize}
    \item 指标替代偏差：把“完成任务”偷换成“通过测试”
    \item 场景抽样偏差：评测集过于理想化，忽略脏数据和边界条件
    \item 观感遗漏偏差：内容正确但输出不可用（排版、可读性、可执行性差）
\end{itemize}
\end{warningbox}

\subsection{评测体系应当是多轴而非单轴}

\begin{importantbox}{访谈中可抽象出的评测矩阵}
\begin{center}

维度 & 代表指标 & 说明 \\
\midrule

\subsection{评测组织：自动化 + 人工审查双轨}

访谈提到评测团队承担两项任务：搭自动化框架与做人工审阅。这不是冗余，而是必要分层。自动化负责规模，人工负责“不可量化但影响留存”的维度。

\begin{knowledgebox}{人工评测仍然必要的三个场景}
\begin{enumerate}
    \item 多步骤任务中“局部正确、整体失败”的隐性错误
    \item 对外展示内容中的审美与叙事连贯性问题
    \item 高风险动作中的权限边界与安全策略误触
\end{enumerate}
\end{knowledgebox}

\subsection{本章小结}

Manus 的飞轮不是“训一次模型解决所有问题”，而是“用真实任务持续校正系统行为”。评测体系必须同时覆盖正确性、稳定性和用户体验。
