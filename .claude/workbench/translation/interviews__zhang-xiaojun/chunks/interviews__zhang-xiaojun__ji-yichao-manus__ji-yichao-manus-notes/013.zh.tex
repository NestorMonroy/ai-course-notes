\section{风险清单与反模式库：避免把通用 Agent 做成“演示系统”}

\subsection{产品层反模式}

访谈反复提醒一个风险：很多团队把“能演示”误当成“能交付”。前者追求短期惊艳，后者追求长期稳定。产品层最常见的反模式包括：只优化首轮响应、不管理长任务状态、不暴露失败原因、不提供可复核中间结果。短期看这些做法能降低开发难度，长期看会让用户信任持续下降。

\begin{warningbox}{产品层 4 大反模式}
\begin{enumerate}
    \item Demo-first：所有优化围绕展示场景，而非真实任务分布
    \item Happy-path-only：只覆盖顺利路径，缺少异常处理
    \item Opaque-output：输出看似完整，但缺少可追溯证据
    \item Metric-theater：指标好看，但用户留存和复购不升反降
\end{enumerate}
\end{warningbox}

\subsection{技术层反模式}

技术层反模式主要来自“复杂度失控”：工具越加越多，策略越来越难学；编排层越来越厚，故障定位越来越慢；模型能力升级后，系统层债务无人治理。访谈中“删工具”“做回放”“强调可观测”这些看似保守的动作，其实是对复杂度的主动管理。

\begin{knowledgebox}{技术层复杂度治理原则}
\begin{itemize}
    \item 默认路径要短：先确保一条路径稳定，再扩展分支
    \item 故障可定位：每次失败都能定位到具体步骤和责任边界
    \item 变更可回滚：任何策略改动都必须可快速撤回
\end{itemize}
\end{knowledgebox}

\subsection{组织层反模式}

组织层风险通常表现为“目标发散 + 节奏失衡”。当团队同时追求太多方向，优先级会名义存在、实际消失；当复盘机制缺失，失败会以不同形式重复出现。访谈中的 GPA 框架与“不做清单”，本质是在解决组织层熵增问题。

\begin{importantbox}{组织层防漂移动作}
\begin{itemize}
    \item 每周只保留少数核心目标，其他事项显式排队
    \item 复盘必须输出“下周停止项”，而不只是“下周计划项”
    \item 关键岗位共享同一指标面板，避免局部最优
\end{itemize}
\end{importantbox}

\subsection{本章小结}

把风险清单显式化，是通用 Agent 团队从“会做功能”走向“会做系统”的分水岭。访谈给出的真正价值，是让团队在扩张之前先具备治理复杂度的能力。
