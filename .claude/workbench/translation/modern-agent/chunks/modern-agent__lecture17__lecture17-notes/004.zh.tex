\section{为什么这种设计很优雅}

讲者把 Codex 的这套设计称为一种 general、unified、minimal 的 tool system。原因在于，一个很小的函数接口就能表达复杂规划行为，而复杂度被交给模型的语义能力处理。

这种设计的好处有三点：

\begin{enumerate}
    \item \textbf{接口小}：工具层只暴露一个 \texttt{update\_plan}，不需要为每种计划操作新增 API。
    \item \textbf{语义强}：创建、更新、重规划都由模型通过参数语义区分。
    \item \textbf{用户可见}：计划不是隐藏在模型内部，而是能作为进度反馈展示出来。
\end{enumerate}

\begin{knowledgebox}{快照而不是补丁}
\texttt{update\_plan} 更像是提交``当前计划状态快照''，而不是对某个 step 发送 patch。这让模型在 replan 时可以整体重排步骤，也让 UI 或日志系统更容易渲染当前状态。
\end{knowledgebox}

\subsection{与文件化计划的关系}

需要注意的是，\texttt{update\_plan} 仍然是上下文级进度工具。对于长任务、跨会话任务、批量生成任务，文件化计划仍然很有必要。上下文内 plan 适合即时执行，文件化 todo 适合恢复、审计和团队协作。

\subsection{本章小结}

Codex 的设计把规划能力压缩到一个极小但表达力足够的工具里。随着 GPT-5.4 这类模型的能力增强，模型可以非常顺滑地用这个工具维护计划状态。
