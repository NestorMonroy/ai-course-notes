\section{update\_plan：执行期的 Live Progress Model}

第二种规划方式是 \texttt{update\_plan}。它不是进入或退出 Plan Mode 的开关，而是一个执行期工具，用于维护当前任务的 checklist / todo list。讲者把它称为一种 live progress model，即 agent 对当前进度状态的内部表示，同时也可以显示给用户。

\texttt{update\_plan} 的 schema 非常简洁：

\begin{lstlisting}[caption={update\_plan 的概念结构}]
{
  "explanation": "Why the plan is being updated",
  "plan": [
    {"step": "Inspect source files", "status": "in_progress"},
    {"step": "Patch implementation", "status": "pending"},
    {"step": "Run verification", "status": "pending"}
  ]
}
\end{lstlisting}

其中每个 step 有三种状态：\texttt{pending}、\texttt{in\_progress}、\texttt{completed}。系统约束最多只能有一个 step 处于 \texttt{in\_progress}，这保证计划始终有清晰的当前焦点。

\begin{importantbox}{同一个工具承载三种动态}
\texttt{update\_plan} 同时承载 plan 的创建、状态更新和 replan。它没有单独的 \texttt{createPlan}、\texttt{modifyStep} 或 \texttt{replan} API，而是每次提交一个新的完整计划快照。
\end{importantbox}

这就是讲者反复强调的 ``plan dynamics''：第一次调用相当于创建计划；后续调用可以把某一步从 \texttt{pending} 推进到 \texttt{in\_progress} 或 \texttt{completed}；如果执行中发现原计划不可行，也可以重新提交一份新的计划快照，并在 \texttt{explanation} 中说明原因。

\subsection{本章小结}

\texttt{update\_plan} 的关键不是复杂 API，而是极简状态模型。模型通过反复提交计划快照，在同一个 agent loop 中完成创建、更新和重规划。
