\section{Model Context Protocol (MCP)}

\subsection{为什么需要 MCP}

LLM 拥有广泛但\textbf{静态}的世界知识——只有在重训时才会更新。要构建真正自主的系统，需要可靠的方式向 LLM 注入动态数据（天气、股价、最新 API 文档等）。

RAG 和 tool calling 是目前最好的答案。但问题在于：

\begin{knowledgebox}{M $\times$ N 连接器问题}
假设有 $M$ 个 LLM 应用和 $N$ 个第三方工具/API。在 MCP 之前，每个应用需要为每个工具编写独立的集成代码——包括认证、错误处理、速率限制等。这导致了 $M \times N$ 个连接器的维护负担。
\end{knowledgebox}

\subsection{MCP 是什么}

MCP（Model Context Protocol）是 Anthropic 于 2024 年 11 月推出的开放协议，为 LLM 提供了一种\textbf{标准化}的工具暴露格式。

\begin{importantbox}{MCP 的核心价值}
MCP 将工具集成从 $M \times N$ 降低到 $M + N$：
\begin{itemize}
    \item 不需要为每个工具重新实现认证、错误处理、速率限制
    \item 使用 JSON-RPC 强制执行一致的输出格式
    \item 从 Language Server Protocol (LSP) 扩展而来，但支持\textbf{主动的}（proactive）agentic workflow，而非 LSP 的纯反应式模式
\end{itemize}
\end{importantbox}

\subsection{MCP 架构详解}

\subsubsection{核心术语}

\begin{itemize}
    \item \textbf{Host}：宿主应用（如 Cursor、Claude Desktop）
    \item \textbf{MCP Client}：嵌入在 Host 中的库（为每个 Server 维护有状态的 session）
    \item \textbf{MCP Server}：轻量级的工具包装器（wrapper）
    \item \textbf{Tool}：可调用的函数（数据源、API 等）
\end{itemize}

\subsubsection{工作流程}

\begin{enumerate}
    \item Client 调用 \texttt{tools/list} 向 MCP Server 查询：``你能做什么？''
    \item Server 返回 JSON 描述每个工具（名称、摘要、JSON Schema）
    \item Host 将这些 JSON 注入模型的 context
    \item 用户 prompt 触发模型，模型输出结构化的 tool call
    \item MCP Server 执行调用，对话继续
\end{enumerate}

\subsubsection{传输层}

MCP 提供两种传输机制：
\begin{itemize}
    \item \textbf{stdio}：标准输入/输出，适用于本地进程通信
    \item \textbf{SSE}（Server-Sent Events）：适用于远程服务通信
\end{itemize}

\subsection{MCP 的局限性}

\begin{warningbox}{当前 Agent 处理多工具的能力有限}
\begin{itemize}
    \item Agent 在面对大量工具时表现不佳——工具描述会快速消耗 context window
    \item API 设计需要面向 AI 原生（AI-native），而非沿用传统的刚性 API 设计
    \item 复杂的 API 参数和嵌套结构会显著降低工具调用的准确率
\end{itemize}
\end{warningbox}

\subsection{本章小结}

MCP 是 AI 编程工具生态的重要基础设施，通过标准化的协议解决了 LLM 与外部工具集成的 $M \times N$ 问题。理解 MCP 的架构（Host $\rightarrow$ Client $\rightarrow$ Server $\rightarrow$ Tool）和通信流程是构建和使用 AI 编程工具的关键。
