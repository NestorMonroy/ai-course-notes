\section{Del protocolo al producto: por qué MCP se convirtió en un parteaguas}

\subsection{No solo resuelve un problema de conexión, sino un problema de colaboración en el ecosistema}
Es fácil malinterpretar la introducción de MCP en la semana 2 como «un protocolo más de tool calling». Pero el sentido más profundo que el curso quiere subrayar es este: \textbf{lo que MCP unifica en realidad es el límite de colaboración del ecosistema de herramientas, no solo la sintaxis de llamada.} En un mundo sin MCP, cada producto de Agent tiene que decidir por su cuenta el método de autenticación, el formato de descripción de herramientas, la estructura de retorno de errores y la gestión del estado de sesión; esto hace que tanto los autores de herramientas como los productos de Agent reinventen la rueda una y otra vez.

\begin{importantbox}{MCP importa porque convirtió las herramientas de una implementación privada de cada proyecto en una interfaz pública del ecosistema}
\begin{itemize}
    \item Para quien provee la herramienta, basta con escribir un MCP Server una vez para que lo reutilicen varios Host, IDE o Agentes;
    \item Para los productos de Agent, ya no hace falta adaptar por separado el schema, el formato de errores y el modelo de permisos de cada herramienta;
    \item Para el usuario, el costo de cambiar de herramienta baja de manera notable, y los flujos de trabajo pueden migrar entre productos.
\end{itemize}
\end{importantbox}

Esto se parece mucho a lo que ocurrió históricamente con LSP. LSP no inventó el «autocompletado» ni «ir a la definición», pero unificó la interfaz entre el editor y el servicio de lenguaje, y con eso elevó la velocidad de innovación de todo el ecosistema. MCP desempeña un papel similar para el ecosistema de herramientas de Agent, solo que el objeto sobre el que actúa pasa de ser «la capacidad del editor» a ser «la capacidad externa que el modelo puede invocar».

\subsection{La parte realmente difícil: la responsabilidad de diseño empieza a aparecer justo después de unificar el protocolo}
Unificar el protocolo no implica que el Agent vaya a usar bien las herramientas de manera natural. Al contrario, en cuanto la interfaz se estandariza, resulta más fácil notar otro problema: \textbf{muchas API existentes sencillamente no fueron diseñadas para que las use un modelo.}

\begin{warningbox}{El diseño de una API AI-native no puede copiar sin más el de una API pensada para desarrolladores humanos}
\begin{itemize}
    \item Demasiados parámetros, anidación excesiva y cambios de estado demasiado implícitos reducen de manera notable la tasa de éxito de las llamadas del modelo;
    \item Si el resultado devuelto carece de un resumen conciso y de una causa de error clara, al modelo le resulta difícil tomar decisiones posteriores;
    \item Si la herramienta no expone el límite de permisos ni describe sus efectos secundarios, es fácil que el Agent haga llamadas de alto riesgo.
\end{itemize}
\end{warningbox}

\subsection{Resumen de la sección}
El sentido de MCP no está en que haya un protocolo más, sino en que ofrece una interfaz pública para el ecosistema de herramientas de Agent. El verdadero desafío que sigue es que la herramienta misma también evolucione de ser «una API pensada para que la lea un desarrollador humano» a ser «una API AI-native que el modelo pueda invocar de manera estable».
