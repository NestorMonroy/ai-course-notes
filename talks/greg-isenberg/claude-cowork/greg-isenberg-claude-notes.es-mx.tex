\section{Introducción: llega la era de los Agent}

Este episodio, presentado por Greg Isenberg, tiene como invitado a Boris, de Anthropic —creador de Claude Code e impulsor central de Claude Co-Work—, en una entrevista. Boris no solo muestra el flujo de operación de Co-Work, sino que también comparte su propio flujo de trabajo y mejores prácticas al usar Claude Code. Este apunte organiza sistemáticamente el contenido de la conversación en cuatro ejes: posicionamiento del producto, forma de uso, mecanismos de seguridad y flujos de trabajo eficientes.

\begin{importantbox}{Idea central}
La esencia de Claude Co-Work es empaquetar la capacidad de Agent de Claude Code en una interfaz que cualquier persona pueda usar; por debajo corre exactamente el mismo Claude Agent SDK que Claude Code. Co-Work puede operar archivos, controlar el navegador y conectarse a cualquier herramienta mediante MCP: no es solo un chat, sino un Agent en el sentido pleno del término.
\end{importantbox}

\begin{knowledgebox}{¿Qué es agentic AI?}
Boris señala que la palabra ``agentic'' se ha usado de forma abusiva en la industria. Su significado central es: \textbf{la IA puede tomar acciones (take action)}, es decir, no se limita a generar texto o buscar en la web, sino que es capaz de usar las herramientas de la computadora e interactuar con el mundo real. Desde muy temprano, Anthropic definió coding, tool use y computer use como los tres ejes centrales de entrenamiento del modelo.
\end{knowledgebox}

\subsection{Resumen de la sección}

Co-Work es el producto de Agent que Anthropic lanzó para usuarios sin conocimientos técnicos: presenta toda la capacidad de Agent de Claude Code a través de una interfaz de escritorio sencilla. Comprender el concepto central de que ``Agent significa poder tomar acciones'' es la base para entender todas las funciones de Co-Work.

\section{Explicación detallada del producto Claude Co-Work}

\subsection{Arquitectura del producto y puntos de entrada}

La aplicación de escritorio de Claude actualmente incluye tres pestañas:

\begin{enumerate}
    \item \textbf{Chat}: la interfaz de conversación predeterminada
    \item \textbf{Co-Work}: el nuevo espacio de trabajo para Agent
    \item \textbf{Code}: es decir, la interfaz de terminal de Claude Code
\end{enumerate}

Boris subrayó en particular que Co-Work invoca directamente el Claude Agent SDK en su base—utiliza exactamente el mismo motor de Agent que Claude Code. Por ahora, Co-Work solo es compatible con macOS; la versión para Windows llegará próximamente.

\subsection{Manejo de archivos: de la organización a la automatización}

El primer escenario que demostró Boris fue la \textbf{gestión de recibos}:

\begin{enumerate}
    \item Montar la carpeta de recibos del escritorio en Co-Work (requiere autorización activa del usuario; no hay permisos por defecto)
    \item Escribir la instrucción: «Tengo una carpeta de recibos, ¿puedes renombrar los archivos por fecha?»
    \item Co-Work leyó cuatro recibos, encontró que a uno le faltaba la fecha y preguntó al usuario de manera proactiva para confirmarlo—Boris llamó a esto \textbf{Reverse Solicitation} (solicitud inversa)
    \item Una vez terminado el renombrado, organizó además los datos en una hoja de cálculo
\end{enumerate}

\begin{importantbox}{Reverse Solicitation (solicitud inversa)}
Cuando el modelo no está seguro de cierta información, \textbf{le pregunta al usuario de manera proactiva} en lugar de asumirla a ciegas. Este comportamiento fue entrenado específicamente y es uno de los mecanismos clave para que el Agent funcione de forma segura. Para el usuario, interactuar con Co-Work se parece más a colaborar con un compañero de equipo responsable y comprometido—que pide aclaraciones cuando lo necesita.
\end{importantbox}

\subsection{Control del navegador: de lo local a la nube}

Cuando Boris planteó «quizá no quiero una hoja de cálculo local, quiero un Google Sheet», Co-Work abrió automáticamente el navegador, navegó a Google Sheets, creó una hoja nueva y llenó los datos fila por fila.

\begin{knowledgebox}{Fundamentos técnicos de las capacidades del navegador}
Co-Work incluye compatibilidad nativa integrada con el navegador Chrome. El modelo puede:
\begin{itemize}
    \item Leer el contenido de la pantalla (similar a computer use)
    \item Hacer clic en botones y llenar formularios
    \item Navegar entre varias pestañas
\end{itemize}
El usuario necesita instalar la Chrome Extension y autorizar cada sitio la primera vez que se visita (puede elegir «permitir una vez» o «permitir siempre»).
\end{knowledgebox}

Boris también demostró el flujo de hacer que Co-Work abriera Gmail y enviara la hoja de cálculo a su colega Amy—el modelo buscó automáticamente el contacto, redactó el cuerpo del correo y guardó un borrador a la espera de confirmación.

\subsection{Ejecución paralela de varias tareas}

\begin{importantbox}{El flujo de trabajo paralelo es el paradigma central}
El modo de uso más poderoso de Co-Work y Claude Code no es completar una tarea a la vez, sino \textbf{ejecutar varias tareas al mismo tiempo}. Mientras una tarea se está ejecutando (por ejemplo, controlar el navegador para elaborar una hoja de cálculo), el usuario puede crear otra tarea nueva (por ejemplo, buscar inspiración para un pódcast de emprendimiento). Boris ejecuta habitualmente entre 5 y 10 instancias de Claude al mismo tiempo.
\end{importantbox}

Greg planteó en la entrevista una idea clave: la empresa debería \textbf{auditar todas sus tareas cotidianas}—revisar cómo el equipo maneja los archivos, usa internet y envía mensajes, para luego identificar qué partes se pueden automatizar con Co-Work.

\subsection{Integración con Slack y colaboración en equipo}

Boris compartió un escenario real que usa varias veces por semana:

\begin{enumerate}
    \item El equipo tiene una hoja de cálculo de seguimiento del proyecto
    \item Co-Work revisa las columnas sin llenar en la hoja
    \item Envía automáticamente un mensaje de recordatorio en Slack al ingeniero correspondiente
\end{enumerate}

Este proceso lo completa Co-Work de manera totalmente autónoma—Boris solo necesita dar la instrucción y luego ir por una taza de café.

\subsection{Resumen de la sección}

Los escenarios de uso principales de Co-Work abarcan la organización de archivos, el control del navegador, la comunicación por correo electrónico/Slack y la ejecución paralela de varias tareas. Para los usuarios no técnicos, Co-Work elimina la barrera técnica de la terminal y conserva a la vez todas las capacidades de Agent de Claude Code. Sus mecanismos de seguridad (autorización, reverse solicitation, entorno aislado) garantizan que las operaciones sean controlables.

\section{Mecanismos de seguridad y confianza}

\subsection{Arquitectura de seguridad en capas}

Boris dedicó una parte considerable a subrayar la inversión de Anthropic en seguridad, que se divide principalmente en las siguientes capas:

\begin{enumerate}
    \item \textbf{Capa del modelo: alineación e interpretabilidad}: la misión central de Anthropic es la seguridad de la IA. En la etapa de entrenamiento del modelo, se garantiza que el comportamiento del modelo corresponda a la intención del usuario mediante alignment (alineación) y mechanistic interpretability (interpretabilidad mecanicista). Boris lo comparó con estudiar la estructura interna de la IA con el método científico, de la misma manera en que se estudian las neuronas del cerebro humano.

    \item \textbf{Capa de ejecución: sandbox de máquina virtual}: en la base de Co-Work hay un entorno de ejecución de máquina virtual completo, que garantiza que ninguna operación afecte el sistema anfitrión del usuario.

    \item \textbf{Capa del usuario: protección contra eliminación}: el nuevo mecanismo de deletion protection le pide confirmación al usuario antes de eliminar un archivo.

    \item \textbf{Capa de red: protección contra Prompt Injection}: cuando el modelo interactúa con internet, cuenta con medidas de protección integradas contra ataques de prompt injection.
\end{enumerate}

\begin{warningbox}{La seguridad sigue evolucionando}
Boris reconoció que estas protecciones no son perfectas y que Anthropic sigue iterando de manera continua. Una de las razones importantes para lanzar el producto lo antes posible es observar y estudiar los patrones de comportamiento del modelo en escenarios de uso real, con el fin de seguir mejorando la seguridad.
\end{warningbox}

\subsection{Modelo de permisos}

Co-Work adopta el \textbf{principio de mínimo privilegio}:

\begin{itemize}
    \item Sistema de archivos: por defecto no tiene acceso a ninguna carpeta; el usuario debe montarlas una por una
    \item Navegador: cada sitio web requiere una autorización independiente en su primer acceso
    \item Confirmación de operaciones: las operaciones sensibles (como enviar correos electrónicos o eliminar archivos) se verifican con el usuario antes de ejecutarse
\end{itemize}

\subsection{Resumen de la sección}

Anthropic construyó un sistema de seguridad en capas que va desde el interior del modelo (alineación, interpretabilidad), pasando por el entorno de ejecución (aislamiento en sandbox), hasta la interacción con el usuario (permisos, confirmaciones). La filosofía de diseño de Co-Work es «seguridad primero, cesión gradual de privilegios».

\section{Skills: módulos de capacidad reutilizables}

\subsection{¿Qué es un Skill?}

Un Skill es, en esencia, un \textbf{patrón reutilizable de ejecución de tareas}. Boris explica que, en la demostración anterior en la que Co-Work generó una hoja de cálculo de Excel, en realidad cargó un skill de Excel preinstalado; esa es la razón por la que el modelo sabía cómo operar Excel de manera correcta.

\begin{importantbox}{La propuesta de valor de un Skill}
Si usas una herramienta o un formato de archivo poco común (como AutoCAD o Salesforce), puedes escribir un Skill personalizado para enseñarle a Claude cómo operarlo. Una instancia de Co-Work con más Skills puede manejar una gama más amplia de tareas y produce resultados de mayor calidad.
\end{importantbox}

\subsection{Recomendaciones de uso}

La recomendación de Boris es \textbf{empezar simple antes de ir a lo complejo}:

\begin{enumerate}
    \item Basta con instalar Co-Work y la extensión de Chrome para empezar a usarlo
    \item No dediques tiempo a personalizar un Skill desde el principio
    \item Considera escribir el Skill correspondiente solo cuando notes que Co-Work no funciona bien en un caso concreto
    \item Los Skills son más adecuados para usuarios avanzados como una manera de optimizar el rendimiento
\end{enumerate}

\subsection{Resumen de la sección}

Un Skill es la capa de capacidad extensible de Co-Work y de Claude Code. Permite que el usuario codifique conocimiento de un dominio en módulos reutilizables, lo que mejora el desempeño del agente en tareas específicas.

\section{Mejores prácticas de Claude Code}

Esta sección se basa en una publicación de Boris en X/Twitter que se volvió viral (99,000 marcadores), así como en su exposición detallada durante el programa.

\subsection{Flujo de trabajo con varios Claude en paralelo}

\begin{importantbox}{La forma de trabajar de Boris}
Boris ejecuta simultáneamente entre 5 y 10 instancias de Claude:
\begin{itemize}
    \item En la terminal local suele mantener varias pestañas abiertas, cada una con su propio checkout de git independiente
    \item Cuando se agotan las pestañas locales, continúa abriendo nuevas tareas en la versión web
    \item Cada mañana, al levantarse, inicia entre 2 y 3 tareas de Claude desde la aplicación de iOS
    \item Aproximadamente la mitad del código actual se produce a través de Claude en el teléfono
\end{itemize}
\end{importantbox}

Boris admite que hace un año jamás habría previsto que su forma de programar terminaría siendo así: repartiendo tareas entre el teléfono y la web, y recorriendo las distintas instancias para revisarlas, como quien administra un equipo de IA.

\subsection{Usar siempre el modelo más potente}

Boris recomienda usar siempre \textbf{Opus 4.5 with Thinking} (no Sonnet):

\begin{knowledgebox}{¿Por qué un modelo más grande resulta más económico?}
Se trata de un hallazgo contraintuitivo: aunque el precio por token de Opus 4.5 es más alto que el de Sonnet, al ser más inteligente:
\begin{itemize}
    \item Consume menos tokens en total para completar la misma tarea
    \item Requiere menos correcciones manuales
    \item El costo y el tiempo totales suelen ser \textbf{menores} que al usar un modelo más pequeño
\end{itemize}
Analogía: contratar a un ingeniero senior tiene un costo por hora más alto, pero como no necesita repetir el trabajo una y otra vez, el costo total puede ser menor que contratar a un ingeniero junior.
\end{knowledgebox}

\subsection{CLAUDE.md como base de conocimiento del equipo}

\begin{importantbox}{Mejores prácticas para CLAUDE.md}
\begin{itemize}
    \item El equipo comparte un archivo CLAUDE.md, integrado al repositorio de Git
    \item \textbf{Se actualiza varias veces por semana, entre todo el equipo}: en cuanto se detecta un error de Claude, se agrega de inmediato la regla de corrección a CLAUDE.md
    \item El formato es completamente libre: es solo un archivo de texto común, sin requisitos de sintaxis especiales
    \item Cada equipo mantiene su propio CLAUDE.md y es responsable de mantenerlo actualizado
\end{itemize}
\end{importantbox}

Boris mostró una captura de pantalla del CLAUDE.md del repositorio de Claude Code: su contenido es muy simple y sencillo, lo que demuestra la idea de que ``no se necesita un formato complejo, solo mantenimiento constante''.

\subsection{Plan Mode: planear antes de ejecutar}

\begin{importantbox}{``Once the plan is good, the code is good.''}
La mayoría de las sesiones de Boris comienzan en Plan Mode:
\begin{enumerate}
    \item Entra en Plan Mode y discute el plan con Claude una y otra vez
    \item Una vez confirmado el plan, cambia al modo Auto-accept Edits
    \item Claude por lo general puede completar todo el PR de una sola vez (one-shot)
\end{enumerate}
Esto coincide con la idea del Spec-driven Development, pero con más flexibilidad: el ``spec'' es solo un plan en forma de texto, sin necesidad de un formato específico.
\end{importantbox}

\subsection{GitHub Action e ingeniería compuesta}

La quinta recomendación de Boris tiene que ver con \textbf{acumular de manera continua el conocimiento del equipo durante la revisión de código}:

\begin{enumerate}
    \item Instalar la GitHub App de Claude en el repositorio mediante \texttt{/install-github-action}
    \item En la revisión del PR, mencionar a @claude para que aplique modificaciones o actualice CLAUDE.md
    \item Esto garantiza que un mismo tipo de problema \textbf{nunca necesite señalarse dos veces}
\end{enumerate}

\begin{knowledgebox}{Ingeniería compuesta (Compound Engineering)}
Boris cita el concepto de ``ingeniería compuesta'' de Dan Schipper: cuando trabajaba en Meta, Boris mantenía una hoja de cálculo con los problemas que surgían en las revisiones de código, y cuando un problema se repetía entre 5 y 10 veces, escribía una regla de lint para automatizar su detección. Ahora, CLAUDE.md más GitHub Action es la versión de esta idea para la era de la IA: en cuanto se detecta un problema, se le pide de inmediato a Claude que actualice la base de conocimiento, para garantizar que el mismo error no se repita.
\end{knowledgebox}

\subsection{Darle a Claude la capacidad de verificar su propia salida}

Boris considera que esto es uno de los \textbf{tres factores clave} para mejorar el desempeño de Claude Code (junto con usar Opus y mantener CLAUDE.md):

\begin{warningbox}{La analogía del ``pintor con los ojos vendados''}
Si un pintor tuviera que trabajar con los ojos vendados, sin importar su habilidad, no podría producir una buena obra. De la misma manera, si Claude no puede ver el resultado de ejecutar el código que escribió, la calidad de su salida se ve muy afectada. Por eso:
\begin{itemize}
    \item Al construir una aplicación web, es indispensable habilitar la extensión de Chrome para que Claude pueda ver el resultado en el navegador
    \item Siempre hay que dejar que Claude ejecute las pruebas, inicie el servidor y revise la salida del simulador
    \item Permitir que Claude se verifique y se corrija a sí mismo es el paso decisivo para pasar de ``aceptable'' a ``excelente''
\end{itemize}
\end{warningbox}

\subsection{Resumen de la sección}

Las mejores prácticas de Claude Code según Boris se pueden resumir en cinco principios centrales:
\begin{enumerate}
    \item \textbf{Paralelismo}: ejecutar varios Claude a la vez, asignando tareas como quien administra un equipo
    \item \textbf{El modelo más potente}: usar siempre Opus 4.5 with Thinking
    \item \textbf{Acumulación de conocimiento}: mantener CLAUDE.md de forma continua como base de conocimiento del equipo
    \item \textbf{Planear primero}: usar Plan Mode para asegurar que el plan sea correcto antes de pasar a la ejecución automática
    \item \textbf{Autoverificación}: permitir que Claude vea y verifique su propia salida
\end{enumerate}
\section{Perspectivas a futuro}

\subsection{La desaparición y el renacimiento del código}

Boris y Dario Amodei predijeron ambos, un año antes, que ``para fin de año la gente ya no escribiría código a mano''. Al grabar el episodio en enero de 2026, Boris comentó que en los últimos dos meses todo su código (entre 200 y 300 PR al mes) fue escrito 100\% por Claude Code, y que él \textbf{no había escrito ni una sola línea de código a mano}.

\begin{knowledgebox}{Pensamiento exponencial vs pensamiento lineal}
Boris enfatiza que el cerebro humano piensa de manera lineal por naturaleza, pero el crecimiento de las capacidades de la IA es exponencial. Si un año antes se hubiera hecho una proyección lineal, jamás se habría imaginado que los modelos ya podrían sustituir por completo la codificación humana. La única manera de hacer una predicción correcta es ``confiar en la curva exponencial y después seguir trazándola''.
\end{knowledgebox}

\subsection{El potencial de Co-Work como plataforma}

Greg y Boris comparan el ecosistema actual de Agentes con los primeros días de la App Store de iPhone:

\begin{itemize}
    \item Cuando la App Store se lanzó en 2008, las aplicaciones más populares eran juguetes como los simuladores de cerveza
    \item Nadie previó que de ahí surgirían Uber, DoorDash o TikTok
    \item Co-Work se encuentra en una etapa similar: la explosión de casos de uso superará la imaginación de todos
\end{itemize}

La tendencia que Boris prevé es que cada vez más trabajo cotidiano trivial (mover datos entre la aplicación A y la aplicación B, conversión de formatos, reportes de estado, etc.) será asumido por los Agentes, mientras que los humanos se concentrarán en el trabajo creativo que realmente disfrutan.

\subsection{Resumen de la sección}

El desarrollo de los Agentes de IA sigue una curva exponencial. El significado de Co-Work como plataforma de Agentes es similar al de la App Store para internet móvil: la verdadera aplicación estrella aún no ha aparecido, pero la infraestructura ya está lista.
\section{Síntesis y ampliación}

El mensaje central de esta entrevista se puede resumir en los siguientes puntos:

\begin{enumerate}
    \item \textbf{Posicionamiento de Co-Work}: la capacidad de Claude Code + una interfaz que cualquiera puede usar, es la puerta de entrada de los usuarios no técnicos al mundo de los agentes
    \item \textbf{Diseño de seguridad}: un sistema de protección de varias capas (alineación del modelo → aislamiento en sandbox → control de permisos → confirmación del usuario)
    \item \textbf{Cambio de paradigma de trabajo}: de «profundizar en una sola tarea» a «gestionar en paralelo varias instancias de IA»; el rol del ingeniero se parece más al de «gestor de un equipo de IA»
    \item \textbf{Composición del conocimiento}: CLAUDE.md es un mecanismo de acumulación de conocimiento a nivel de equipo, que asegura que los errores no se repitan
    \item \textbf{Ciclo de verificación}: que el agente pueda ver y verificar su propia salida es clave para mejorar la calidad
\end{enumerate}
